# ЕЦЛ: восстановленный проект, Telegram и MAX

Проект восстановлен 16 сентября 2026 года из действующей серверной сборки `170.168.112.23`. Это воспроизводимая JavaScript-версия, а не восстановление потерянных TypeScript/TSX-файлов в исходном виде. Серверные классы сохранены в CommonJS, клиентский bundle отформатирован и используется как редактируемый исходный JavaScript, включая поставленный React runtime. При сборке браузерный код минифицируется и получает имя с хешем.

## Сборка и проверка

Требуется Node.js 20.19+; рабочий сервер использует Node.js 22.

```sh
cd recovered
npm ci
npm run build
npm test
npm run test:integration
```

Последняя команда запускает временную локальную PostgreSQL 17, применяет миграции и проверяет настоящий HTTP API на синтетических данных. Рабочая база и настоящие токены не используются. Для разработки на другой архитектуре npm устанавливает соответствующий пакет `embedded-postgres`.

## Где менять код

- `apps/api/src` — серверный код; сборка создаёт `apps/api/dist`.
- `apps/office-web/src/app.js` — общий интерфейс входа по телефону и паролю, админской выдачи доступа и восстановления сессии для браузера, Telegram и MAX.
- `apps/office-web/src/assets/app.css` — стили; `index.html` — шаблон страницы.
- `apps/driver-web/src` — сохранённая серверная сборка отдельного закрытого кабинета водителя; публичный интерфейс использует офисную сборку с доступом по роли.
- `packages/contracts/src` — восстановленные JavaScript-контракты.
- `infra/db/migrations/018_phone_password.sql` — учётные данные и защита от перебора паролей.
- `scripts/bootstrap-password.cjs` — однократная выдача первого пароля существующему администратору (телефон через stdin, закрытый stdout).
- `infra/db/migrations/017_max_auth.sql` — добавочная миграция MAX; старые Telegram-приглашения сохранены.
- `infra/deploy/transport-miniapp.nginx.conf` — CSP с поддержкой обоих SDK; сборка обновляет хеш встроенного скрипта темы.
- `RECOVERED_BASELINE_SHA256.json` — контрольные суммы исходной рабочей версии до изменений.

Секреты поступают через переменные окружения. `MAX_BOT_TOKEN` никогда не передаётся браузеру. Для рабочего окружения применяются существующие ограничения ролей и областей доступа; номер и пароль выдаёт администратор без изменения ролей. Связывание мессенджеров через старые API приглашений сохранено для совместимости. Основной интерфейс использует телефон и пароль.

## Фото водителя и просмотр документов

В «Рейсы → Документы» водитель может выбрать файл или нажать «Сфотографировать». Камера показывает снимок до отправки: доступны «Переснять» и «Использовать фото», после выбора нужно нажать «Загрузить документ». В контрольном осмотре те же действия доступны у каждого пункта; фотографии передаются вместе с осмотром. Если встроенная камера недоступна, есть вызов камеры устройства.

Документовед видит фотографии в карточках документов, механик — в отчёте КО. Нажатие на миниатюру открывает просмотр с увеличением внутри приложения. PDF и скачивание документов работают как прежде. Просмотр фотографий использует существующий авторизованный API и права области доступа. Камера создаёт JPEG; лимиты документов (10 МБ) и фото КО (5 МБ, 4 фото на пункт) сохранены.

Браузерная проверка: `npm run test:driver-photos:browser` (Playwright через `PLAYWRIGHT_MODULE`, при необходимости `CHROME_PATH`). Сценарий запускает отдельную временную базу и использует тестовую камеру Chromium.

## Возврат КО и удаление фотографий

У водителя рядом с «Контрольный осмотр» отображается число осмотров на доработке. Список содержит рейсы и замечания механика; «Исправить КО» открывает сохранённые ответы, комментарии и фотографии. Черновик исправления сохраняется на устройстве, в том числе после перезагрузки. При повторной отправке загружаются только добавленные фото, исходные снимки используются повторно. Счётчик уменьшается после отправки исправлений, а не после открытия отчёта. История версий сохраняется; изменившийся шаблон не заставляет заполнять возвращённый осмотр заново.

Администратор может удалять фото осмотров в доступной ему области в любое время. У обычного механика такого права нет. В «Сотрудники → карточка механика → Главный механик» администратор назначает отдельное право по области ответственности. Главному механику удаление доступно через один календарный месяц после загрузки; до этого интерфейс показывает дату доступности. Право не назначается никому автоматически и не меняет доступ к персональным данным. Отзыв применяется к следующим запросам без повторного входа.

Ручное удаление подтверждается пользователем: содержимое фото удаляется, а ответы, ссылки в истории, исходные дата/размер/контрольная сумма и отметка удаления остаются. Удалённый снимок недоступен для просмотра или повторного использования. В рабочем месте сотрудника доступны также фотографии предыдущих версий осмотра.

После принятия осмотра механиком сервер сжимает его фотографии: WebP, качество 55, до 1600 пикселей по длинной стороне, без увеличения и обрезки. При перекодировании учитывается поворот камеры и удаляются метаданные снимка. Более крупный результат не заменяет исходник; уже обработанные снимки не сжимаются повторно. Необрабатываемые изображения сохраняются до окончания срока хранения.

Все фотографии КО автоматически удаляются через **три календарных месяца от загрузки**, независимо от статуса осмотра, включая неотправленные загрузки. Дата автоудаления показана в интерфейсе. Фоновая обработка запускается при старте API и каждую минуту; после простоя приложение обрабатывает накопившиеся снимки. Доступ к просроченному фото закрывается сразу по сроку. Сохраняются ответы, история, исходные метаданные и отметка автоматического удаления. Данные документов вне КО этой политикой не затрагиваются.

Проверки: `npm run test:inspections` (сжатие и временная PostgreSQL), `npm run test:inspections:browser` (доработка), `npm run test:inspections:retention:browser` (просмотр сжатых фото и автоудаление). Миграции 061, 062 и 064 добавляют жизненный цикл фотографий и отдельное право главного механика. После обновления обработка применяется также к ранее загруженным фото. Для изолированных тестов фоновый запуск выключен; переменная `INSPECTION_PHOTO_MAINTENANCE_ENABLED` позволяет явно включить или выключить его.

## Планирование для менеджеров

Раздел сохраняет общий план на дату и зону ответственности, назначения водителей и машин, а также дополнительные поля выбранной клиентской формы. Перенесены 15 вариантов подачи из листа «Планировка» и добавлена общая форма. В конструкторе можно создавать и копировать формы, менять колонки, подстановки и обязательность, назначать форму по умолчанию. Старые планы сохраняют свою версию формы. Календарь позволяет копировать дни и диапазоны, протягивать назначения по сетке, просматривать детали при наведении и редактировать назначения. Изменённые дни сохраняются единым пакетом с защитой от конфликтов. Подробности работы, прав доступа, проверок и установки: [PLANNING.md](../docs/PLANNING.md).

## Команда

Встроенная корпоративная среда: каналы, треды с вложенными ветками, личные чаты и база знаний. Администратор читает всю переписку в своих областях, включая личные чаты сотрудников; это явно обозначено в интерфейсе. ## Особенности MAX

Адрес для настроек бота: `https://170.168.112.23/?messenger=max`.

`POST /api/v1/auth/max` принимает `{initData, invitationToken?}`. `POST /api/v1/access/max-invitations` принимает `{userId, maxUserId}` и требует администратора с правами на целевого сотрудника. Числовые ID Telegram и MAX не объединяются автоматически.

Кнопка скачивания в MAX создаёт защищённую временную ссылку и вызывает `WebApp.downloadFile` после отдельного нажатия. Максимальный файл — 8 МиБ, срок ссылки — 60 секунд, ссылка одноразовая; HEAD её не погашает. Перед выдачей файла сервер повторно проверяет сессию. Хранятся максимум два ожидающих файла на сотрудника и 32 МиБ ожидающих файлов суммарно в памяти. Это лимит хранилища ожидающих файлов, а не общий лимит памяти процесса. Перезапуск удаляет ожидающие файлы; их можно подготовить заново.

Встроенная переписка с отделами остаётся ранее реализованной интеграцией Telegram. Добавление входа MAX не включает рассылки или сообщения сотрудникам.

## Обновление и откат

`infra/deploy/apply-phone.py` устанавливает текущее обновление по телефону и паролю без дополнительных секретных аргументов; проверяет свежий baseline API и web-root. Исторический `infra/deploy/apply-max.py` выполняется на сервере только с подготовленным пакетом релиза и отдельным закрытым файлом токена. Он проверяет контрольные суммы исходной версии, сохраняет PostgreSQL-архив, настройки, старую API-сборку и веб-каталог, применяет добавочную миграцию и переключает сервис. При неуспехе проверки готовности возвращает предыдущие файлы и настройки. Добавочная миграция сохраняется, чтобы не удалять новые данные.

При последующих обновлениях нужно заново снять контрольные суммы текущей версии для проверки конкурентных изменений; прежний baseline намеренно не позволяет применить начальный пакет поверх другой версии.

Настройка URL Mini App выполняется владельцем в кабинете MAX для бизнеса. API-токен бота не предоставляет сессию входа в этот кабинет. Полный запуск необходимо подтвердить в настоящем клиенте MAX с учётной записью сотрудника; вход выполняется по выданным телефону и паролю.
