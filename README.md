# ЕЦЛ — приложение управления перевозками

Репозиторий содержит сервер приложения, веб-интерфейсы, миграции PostgreSQL,
локальные интеграции и проверки. Основной код находится в `recovered/`:
он восстановлен из работающей JavaScript-сборки и развивается в этом формате.
Подробности: [описание приложения](recovered/README.md).

## Структура

| Каталог | Содержимое |
| --- | --- |
| `recovered/apps/api/src` | Серверный API |
| `recovered/apps/office-web/src` | Основной веб-интерфейс |
| `recovered/apps/driver-web/src` | Сохранённый отдельный интерфейс водителя |
| `recovered/packages` | Общий код и контракты |
| `recovered/infra/db/migrations` | Версионированные изменения схемы базы |
| `recovered/infra/deploy` | Конфигурация и существующие сценарии установки |
| `tests` | Автоматические проверки и тестовое окружение |
| `integrations` | Интеграции и инструменты импорта |
| `native` | Приложения Tauri для macOS, Windows, Android и iOS; нативная часть на Rust |
| `docs` | Описание модулей и эксплуатационные инструкции |

Клонируйте весь репозиторий: проверки и интеграции используют пути за пределами
`recovered/`.

Приложения для компьютеров и телефонов собираются отдельно из `native/` и используют
существующий API. Инструкции, платформенные требования и ограничения локального
подключения: [приложения ЕЦЛ](docs/NATIVE_APPS.md).
Установщики macOS, Windows и Android доступны в [GitHub Releases](https://github.com/alexandrosstagiros-png/eclapp/releases/latest).
Подписанные обновления загружаются из приложения; подробности — [обновления ЕЦЛ](docs/NATIVE_UPDATES.md).

## Сборка и проверки

Для новых окружений используйте Node.js 22 и npm. Команды из корня репозитория:

```sh
cd recovered
npm ci
npm run build
npm test
npm run test:integration
npm run test:inspections
npm run test:recruitment:onboarding
```

Интеграционные проверки создают временную PostgreSQL 17 и синтетические данные.
Не задавайте им реквизиты рабочей базы. Для запуска PostgreSQL нужен обычный
пользователь операционной системы, а не `root`.

Браузерные проверки запускаются отдельно; им нужны Playwright и Chromium.
Доступные команды и дополнительные условия описаны в
[README приложения](recovered/README.md) и `recovered/package.json`.

Файлы запуска `.command` и настройки локальной 1С содержат пути исходного
компьютера. Перед использованием на другом компьютере настройте их под свою
установку; для сборки и CI эти файлы не нужны.

## Работа с изменениями

1. Создайте отдельную ветку для задачи.
2. Измените код и выполните проверки, относящиеся к задаче.
3. Откройте pull request в `main` и дождитесь успешного CI.
4. После проверки объедините изменения и подготовьте выпуск.

GitHub Actions выполняет сборку, модульные и интеграционные проверки.
Обновления сервера после успешного CI текущего `main` поддерживают два способа
доставки: workflow `Deploy VK Cloud` по SSH или опрос GitHub самой ВМ по HTTPS.
Если входящий SSH из GitHub недоступен, включается серверный таймер
`ecl-pull-update.timer`; секреты деплоя в GitHub ему не нужны, а
`VK_DEPLOY_ENABLED` остаётся выключенным. Для доставки по SSH эта переменная
включается после настройки сервера и секретов. Установка, перенос PostgreSQL,
HTTPS и оба способа обновлений описаны в
[инструкции VK Cloud](docs/VK_CLOUD_DEPLOYMENT.md).

## Рабочее окружение

Ограничьте право изменять `main`. Файлы `.env`, ключи, рабочие выгрузки, вложения,
резервные копии и каталог `.local/` не должны попадать в Git. Приватность
репозитория не заменяет отдельное хранение секретов.

Перед установкой версии на рабочий сервер проверьте изменения на тестовом
окружении, создайте резервную копию базы и файлов и подготовьте возврат
предыдущей сборки. Изменения базы требуют отдельного плана восстановления.
Существующие сценарии в `recovered/infra/deploy` относятся к конкретным
обновлениям; перед повторным применением нужно проверить их условия и baseline.

Для установки на новую ВМ Ubuntu 24.04 используйте `deploy/vk-cloud/` по
[инструкции VK Cloud](docs/VK_CLOUD_DEPLOYMENT.md). Перед включением обновлений
проверьте приложение, восстановление резервных копий и внешнюю доступность.
Тестовое окружение и резервное копирование вне рабочего сервера настраиваются
отдельно.
