# Реализованная поддержка MAX

Состояние на 16 сентября 2026 года: серверная часть, клиент и миграция MAX установлены на `170.168.112.23`. Привязка URL в кабинете MAX и вход реального сотрудника из клиента MAX ещё не подтверждены.

## Восстановленный проект

Код находится в `recovered/`. Серверный CommonJS восстановлен из работающего API, браузерный JavaScript отформатирован из поставленного bundle и стал входом воспроизводимой сборки. Потерянные исходные TypeScript/TSX-файлы не выдаются за восстановленные оригиналы. Инструкции сборки — `recovered/README.md`.

## Авторизация и права

- `POST /api/v1/auth/max` проверяет оригинальные подписанные `initData` с токеном MAX, срок действия и повторы. Внутренний сотрудник определяется отдельно по `(provider='max', provider_user_id)`.
- `POST /api/v1/access/max-invitations` создаёт одноразовое приглашение `{userId,maxUserId}`; нужна действующая сессия администратора и права на каждую область сотрудника.
- Только активные, одобренные сотрудники с разрешённой ролью и областями доступа получают сессию. MAX не назначает роли и не создаёт сотрудника по имени, телефону или совпадению числового ID Telegram.
- Погашение replay, привязка, погашение приглашения и выдача сессии выполняются транзакционно. Отзыв сотрудника гасит сессии и приглашения обоих каналов.
- Срок `initData` — 300 секунд. Повторное открытие в том же WebView восстанавливает MAX-сессию через `/me`; использованные `initData` без сохранённой сессии требуют нового запуска из бота.
- Токен бота хранится в серверном `/etc/transport-miniapp.env`, в браузер и исходники не включён.

## Данные

Миграция `017_max_auth.sql` добавила `max` в ограничения каналов `sessions`, `workflow_attendance`, `channel_identities` и отдельную таблицу `max_invitations`. Telegram-таблица `invitations` сохранена для совместимости с закрытым демо, использующим ту же базу `transport`.

Список сотрудников показывает состояния привязки Telegram и MAX отдельно и позволяет выпустить MAX-приглашение существующему сотруднику.

## Интерфейс и документы

Клиент определяет MAX по его стартовым параметрам или `?messenger=max`, загружает `https://st.max.ru/js/max-web-app.js` и использует `window.WebApp`. Telegram использует свой SDK и прежний маршрут входа.

Для загрузки файла в MAX используется временная ссылка `/api/v1/max/downloads/:token`: создание доступно авторизованному сотруднику MAX, выдача повторно проверяет его сессию. Ссылка одноразовая, живёт 60 секунд, HEAD её не погашает. Максимальный файл — 8 МиБ, максимум два ожидающих файла на сотрудника и 32 МиБ ожидающих файлов в памяти. Пользователь отдельно нажимает кнопку скачивания, вызывающую `WebApp.downloadFile`.

Nginx разрешает SDK и веб-встраивание обоих мессенджеров. HTTP остаётся перенаправлен на HTTPS, dev/demo-вход извне закрыт. Встроенная переписка с отделами остаётся существующей Telegram-интеграцией; рассылки MAX не добавлялись.

## Проверки

- 66 модульных тестов: подписи, сроки, типы данных, права, приглашения, хранилище скачиваний и клиентские функции.
- 21 интеграционный сценарий на отдельной PostgreSQL 17 и настоящем HTTP API (Node выводит 22 теста с учётом родительского).
- Чистая БД разворачивается мигратором с созданием ограниченной роли; тесты используют только синтетические записи и токены.
- Проверены одновременный вход, replay, независимость одинаковых ID Telegram/MAX, права на рейсы, явка, отзыв доступа и приглашений, HEAD/GET, одновременное скачивание, файлы до 8 МиБ.
- После установки: HTTPS и оба health-маршрута — 200, рейсы без входа — 401, dev/demo-маршрут — 404. Правильно подписанный запрос непривязанного синтетического MAX-пользователя отклонён с 401.
- В обычном браузере опубликованный экран входа MAX отрисован и SDK загрузился. Реальный клиент MAX и авторизованное устройство сотрудника остаются отдельной финальной проверкой.
