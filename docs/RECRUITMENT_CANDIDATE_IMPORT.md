# Перенос кандидатов из рабочей таблицы

Перенос работает с существующими областями, сотрудниками и потребностями модуля «Рекрутинг». Он не создаёт аккаунты, права или потребности. Перенос проектов из `integrations/recruitment-import` и перенос кандидатов имеют разные пространства идентификаторов. Ранее перенесённые потребности следует выбрать по существующим UUID.

Подготовка текущей книги выполнена в `.local/recruitment-candidate-import/`: 9 512 основных строк без двух тестовых записей, 2 093 строки с непригодным обязательным полем требуют проверки. Выборка и принятые решения записаны в `policy.json`, результат создания карточек — отдельно в `apply.json`. Каталог и результаты содержат персональные данные, имеют режимы 0700/0600 и исключены из Git через `.local/`.

## Модель переноса

- Кандидат создаётся один раз после явного решения о совпадениях. Один телефон автоматически не объединяет людей.
- Каждая выбранная строка становится отдельным `recruitment_contacts` с `result=inquiry` и `origin=import`. Повторные обращения сохраняют собственные источник и дату.
- Проверенная дата исходной записи сохраняется с исходным часовым поясом. Пустые, ошибочные, будущие и вычисленные формулой даты остаются `NULL`. Особенно важны самоссылки дат на листе «Свои авто»: сохранённый результат формулы не считается проверенным событием.
- Для созданных карточек полный исходный текст, формулы, значения XML, координаты и карта решения сохраняются в административной `recruitment_candidate_imports`. Обычный пользователь приложения не имеет прямых прав чтения этой таблицы. Отдельная `recruitment_import_rows` хранит исходные строки для просмотра в «Импорт Excel» с проверкой роли и области доступа. Аудит содержит только технические идентификаторы, количества и SHA файла.
- Исторические галочки СБ, трудоустройства и увольнения не создают новые события приложения. При явном выборе существующей потребности можно создать отклик только на этапах `new` или `reserve`. Подтверждение СБ, стажировки, выхода и следующие задачи оформляются после сверки через приложение.
- «Пальма», «Неликвид», «ГРУЗЧИКИ», «Лист9», «ОФИС» сначала сохраняются в `archive.json`, затем отдельным этапом загружаются как исходный архив приложения. «Проекты», «Параметры» и «Отчёт» также сохранены для просмотра исходных значений. Эти листы, исключённые примеры и строки без имени/телефона не создают кандидатов или новые потребности.

## 1. Подготовить неизменяемый снимок

Нужен bundled Python с `openpyxl`; путь можно получить через `load_workspace_dependencies` в Codex. Из корня репозитория:

```sh
"/path/to/bundled/python3" integrations/recruitment-candidates-import/prepare.py \
  --workbook "/path/to/Группа#4 (1).xlsx" \
  --output .local/recruitment-candidate-import \
  --document-id group-4-candidates \
  --timezone Europe/Moscow \
  --as-of 2026-09-24
```

`--document-id` — постоянный идентификатор исходной книги; не менять его ради обхода проверки повторного переноса. Скрипт читает книгу, не пересчитывает формулы и не изменяет её. Существующие выходные файлы не перезаписываются. Для нового снимка нужен отдельный каталог и сверка с предыдущим снимком.

Выходные файлы:

| Файл | Содержимое |
| --- | --- |
| `batch.json` | Исходные строки двух основных листов, нормализованные предложения, проблемы качества |
| `archive.json` | Отдельный архив остальных кандидатских листов |
| `resolution.json` | Карта сотрудников, областей, источников, потребностей и решений по выбранным строкам |
| `summary.json` | Количества без имён и телефонов |
| `policy.json`, `duplicate-policy.json` | Политика выбора карточек и признаки неоднозначных/повторных обращений |
| `extra-archive.json` | Заголовки листов, прочие листы и исключённые примеры; создаётся дополнительным экстрактором |
| `main-remainders.json` | Остальные непустые строки основных листов, не вошедшие в карточки или примеры |

## 2. Заполнить карту решений

`recruiters` сопоставляет каждое исходное написание имени действующему аккаунту. `targets` сопоставляет лист области работы и типу `driver` / `carrier`. Название листа само по себе не устанавливает тип. `sources` содержит точные значения справочника приложения. `demands` сопоставляет ключ `лист:исходная локация` существующей потребности.

Ниже условный фрагмент. Все UUID необходимо взять из приложения. Здесь они обозначены словами, поэтому такой пример не пройдёт проверку без заполнения.

```json
{
  "recruiters": { "Исходное имя": "UUID_АККАУНТА" },
  "targets": { "Свои авто": { "responsibilityScopeId": "UUID_ОБЛАСТИ", "kind": "driver" } },
  "sources": { "Авито": "avito" },
  "demands": { "Свои авто:Исходная локация": "UUID_ПОТРЕБНОСТИ" },
  "records": {
    "Свои авто:3": {
      "action": "import",
      "candidate": { "mode": "new" },
      "disposition": "active",
      "demand": "mapped",
      "stage": "new",
      "acknowledgedIssues": ["unverified_inquiry_date"]
    }
  }
}
```

Сохраните созданные `schemaVersion`, `documentId`, `sourceSha256`. Все строки без решения остаются `pending`; можно выбрать только пилот одного проекта. По выбранным строкам нельзя оставлять нерешённые ошибки.

Поля решения:

| Поле | Значение |
| --- | --- |
| `action` | `import`, `pending` либо `exclude` с непустым `reason` |
| `candidate` | `{ "mode":"new" }`, `{ "mode":"existing", "id":"UUID" }` или `{ "mode":"record", "sourceKey":"Свои авто:3" }` |
| `disposition` | Явно `active` либо `archive`; отсутствие отказа в источнике не подтверждает активность |
| `demand` | `none` без отклика, `mapped` из общей карты или UUID существующей потребности |
| `stage` | При создании отклика явно `new` либо `reserve` |
| `application` | `reuse`, если кандидат уже связан с выбранной потребностью; существующий отклик не изменяется |
| `acknowledgedIssues` | Все коды `issues` исходной строки, рассмотренные ответственным сотрудником |
| `corrections` + `evidence` | Исправленные `fullName`, `phone`, `city`, `occurredAt` и основание исправления. Нельзя ставить вымышленные значения для прохождения проверки |
| `recruiterId`, `target` | При необходимости явное решение для одной строки вместо общей карты |
| `notes` | До 4 000 символов: заметка новой карточки и отдельного исторического обращения. При повторном обращении существующая карточка не перезаписывается |

`candidate.mode=record` разрешён только для выбранной строки с `mode=new` в том же пакете и совпадающими телефоном, типом, областью, ответственным. `existing` не обновляет существующую карточку; телефон, область, тип, ответственный и состояние архива должны совпадать с согласованным решением. При общем номере нескольких людей импорт приостановлен до разрешения конфликта в модели данных/контактов. Добавлять фиктивные телефоны запрещено.

Если кандидат уже связан с потребностью, `application=reuse` сохраняет её текущий этап и историю. Историческое обращение можно привязать к этому отклику без повторной заявки. Для внешнего рекрутера дополнительно проверяются действующий внешний доступ и разрешённые потребности; автоматически доступ не выдаётся.

Для согласованной политики технического владельца предусмотрен офлайн-скрипт `prepare-resolution.cjs`. Он сохраняет резервную копию карты, создаёт `policy.json` и `duplicate-policy.json`, не подключается к БД. Требуются явные `--scope` и `--technical-owner`. Все записи получают `disposition=archive`, `demand=none`; исходный рекрутер, локация, источник, комментарий и причина отказа переносятся как текст в заметки. Администратор отмечен техническим владельцем, а не исходным рекрутером. Неизвестный канал получает `other`, его исходное название сохраняется.

Этот вариант выбирает только строки с валидными обязательными полями, исключает все межлистовые телефоны и все группы одного телефона с разными/неполными именами. Совпадения нормализованного имени и телефона внутри одного листа становятся повторными обращениями. По имеющемуся снимку это 5 781 обращение и 5 333 карточки; 3 731 строка доступна в приложении как «Требуют разбора». Автоматического разрешения конфликтов нет. Направления по умолчанию (`Свои авто=driver`, `Наемные авто=carrier`) помечены `assumed`; изменение на `confirmed` допустимо только после подтверждения соответствия.

```sh
node integrations/recruitment-candidates-import/prepare-resolution.cjs \
  --directory .local/recruitment-candidate-import \
  --scope UUID_ОБЛАСТИ --technical-owner UUID_АДМИНИСТРАТОРА \
  --own-kind driver --hired-kind carrier --direction-status assumed
```

## 3. Создать карточки и исторические обращения

CLI подключается только к настроенной локальной PostgreSQL через `integrations/local-app/runtime.cjs`. Он не принимает URL БД, не читает произвольный `.env` и не поддерживает удалённую запись. Нужны миграции `036_recruitment_workflow.sql` и `038_recruitment_candidate_import.sql` и локальный активный администратор с доступом к персональным данным каждой выбранной области. Номер 037 в этой поставке не используется.

```sh
# Только SELECT, транзакция READ ONLY. Без выбранных строк работает офлайн.
node integrations/recruitment-candidates-import/import-local.cjs --preview

# Проверяет реальные INSERT/ограничения, затем откатывает всю транзакцию.
node integrations/recruitment-candidates-import/import-local.cjs --dry-run

# Записывает только выбранные проверенные строки одной транзакцией.
node integrations/recruitment-candidates-import/import-local.cjs --apply
```

Другой каталог указывается как `--directory PATH`. По умолчанию запускается `--preview`. Детальный результат сохраняется приватно в `preview.json`, `dry-run.json` или `apply.json`; stdout содержит только количества. При ошибке выбранных строк `preview` возвращает код процесса 2 и список `sourceKey/code` в файле. Например, `phone_match_requires_explicit_identity_resolution` требует решения о совпадении, а `recruiter_missing_or_not_authorized` — проверки аккаунта и доступа.

После согласования карты сначала запустить `preview`, затем `dry-run`, сопоставить результат с выбранной политикой и только потом `apply`. Наличие `resolution.json` само по себе не означает выполненный импорт: фактический результат записывается в `apply.json`.

## 4. Сохранить остальные исходные строки в приложении

Этот этап требует миграции `039_recruitment_import_rows.sql`. Экстрактор читает ту же книгу и проверяет её SHA, дополняет снимок заголовками, другими листами, примерами и всеми непустыми строками основных листов вне `batch`. Формулы сохраняются как текст и вычисленные ранее значения, без пересчёта.

```sh
"/path/to/bundled/python3" integrations/recruitment-candidates-import/extract-stage-source.py \
  --workbook "/path/to/Группа#4 (1).xlsx" \
  --directory .local/recruitment-candidate-import
```

Загрузчик `stage-local.cjs` использует пять приватных файлов: `batch.json`, `archive.json`, `extra-archive.json`, `duplicate-policy.json`, `main-remainders.json`. Запускать его следует **после успешного завершения создания карточек**: связи со строками определяются по фактически записанной истории переноса, документу, исходной строке и полной области доступа.

```sh
node integrations/recruitment-candidates-import/stage-local.cjs --preview \
  --directory .local/recruitment-candidate-import --scope-id UUID_ОБЛАСТИ \
  --workbook "/path/to/Группа#4 (1).xlsx"

node integrations/recruitment-candidates-import/stage-local.cjs --dry-run \
  --directory .local/recruitment-candidate-import --scope-id UUID_ОБЛАСТИ \
  --workbook "/path/to/Группа#4 (1).xlsx"

node integrations/recruitment-candidates-import/stage-local.cjs --apply \
  --directory .local/recruitment-candidate-import --scope-id UUID_ОБЛАСТИ \
  --workbook "/path/to/Группа#4 (1).xlsx"
```

`preview` использует транзакцию только для чтения, `dry-run` проверяет вставки с полным откатом, `apply` сохраняет весь архив одной транзакцией. CLI выводит только количества. Он не создаёт и не изменяет карточки, роли, права, отклики или задачи. Некорректное обязательное поле не препятствует сохранению строки как исторического источника. Связь с карточкой, флажки источника и текущее состояние подбора остаются разными сведениями.

API просмотра: `GET /api/v1/recruitment/import-rows` и `GET /api/v1/recruitment/import-row`. Обязателен `responsibilityScopeId`; для одной строки также `id`. Список поддерживает `status`, `sheet`, `recruiter`, `search`, `page`, `pageSize` до 100. Проверяется действующая сессия, внутренняя роль и право на персональные данные точной области. Общий поиск по чужим областям и доступ внешних рекрутеров запрещены.

## Повторный запуск и защита актуальных данных

Идентификаторы детерминированы от document ID, листа, строки и типа сущности. Точный повтор ничего не создаёт и не обновляет, даже если кандидат после импорта уже изменён в приложении. Изменение исходной строки или её карты решений блокирует повторную запись.

Другой SHA той же книги блокируется целиком: перестановка строк не должна незаметно создать новых людей. Этот инструмент переносит один проверенный снимок и не является синхронизацией работающего Excel. Для дельты нужен отдельный просмотр изменений и подтверждение идентичности записей. Назначения и права сотрудников также должны оставаться действующими на момент запуска.

Повтор загрузки исходного архива также не создаёт записей и событий аудита. Несовпадение содержимого, признаков проверки, связи с карточкой или состава ранее сохранённых строк отменяет транзакцию. Это предохраняет просмотр исторического источника от незаметной замены после начала работы команды.

## Проверка реализации

`node --test tests/recruitment-candidate-import.test.cjs` создаёт временную PostgreSQL только с синтетическими данными. Проверяются обязательные сопоставления, карантин, повторные обращения, отсутствие новых дат и событий этапов, права областей, ссылки на существующие потребности, отсутствие ПДн в аудите, полный откат, повторный запуск и сохранение изменений приложения.

`node --test tests/recruitment-import-rows.test.cjs` проверяет атомарность сохранения исходных строк, повторный запуск, соответствие снимка, связи с карточками, отсутствие ПДн в аудите и ограничения API. `node tests/recruitment-import-rows-browser.cjs` проверяет вкладку, фильтры, просмотр исходных полей и переход в карточку. Эти проверки выполняются на отдельной временной базе с синтетическими данными.
