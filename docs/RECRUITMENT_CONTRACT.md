# Native recruiting module contract

The section follows EspoCRM's candidate/card/activity approach; it is a native extension of this React/Nest/PostgreSQL application, not bundled EspoCRM or its paid extensions. No external service calls or production fixtures.

## Access and HTTP

All routes `/api/v1/recruitment`, Bearer session, staff roles manager/dispatcher/recruiter/access_admin. Internal access is company-wide: at least one current personalDataVisible grant in a legal entity opens recruitment across its projects. The expansion is local to recruitment; stored grants and other modules are unchanged. Role alone does not grant access. The external_recruiter role retains its exact scope grant plus an active, unexpired explicit request assignment and the restrictions below. Revalidate current session and grants inside each transaction. Candidates retain their original project as provenance and can participate in requests in other projects of the same company without copying their card. Responses no-store. IDs UUIDs. Every record PUT is a complete record with id, responsibilityScopeId and version (0 creates; existing version required). Return the saved record (version incremented, timestamps). Conflict 409, invalid 400, denied 403. No delete: statuses preserve history. Server validates same-company candidate references, exact request/application project routing, recruiter eligibility and safe HTTPS hh.ru links. All dates with time are ISO instants; date-only fields YYYY-MM-DD.

- GET `/context` -> `{scopes:[{legalEntityId,regionId,projectId,responsibilityScopeId,legalEntityName,regionName,projectName,scopeName,timeZone}]}`
- GET `?responsibilityScopeId=...` -> `{requests:[],candidates:[],applications:[],tasks:[],events:[],recruiters:[{id,name}],integrations:{hh:'external_links',oneC:'not_connected',messengers:'not_connected'}}`. Read the company collection or optional project filter with explicit bounded limit/error rather than silent truncation.
- PUT `/requests`, `/candidates`, `/applications`, `/tasks` -> saved record.
- GET `/reminders` -> `{tasks:[task with candidateName,scopeName],serverTime}`; only open tasks assigned to current actor, dueAt <= now, across current permitted scopes. Can be polled 60s by global notice. No external delivery.

Every record includes id, legalEntityId, regionId, projectId, responsibilityScopeId, version, createdAt, updatedAt. Complete body may include server read-only fields which are ignored. Missing optional strings normalize empty. Null optional UUID/time values.

### Company collections (migration 054)

Internal GET `/recruitment`, `/worklist`, `/import-rows`, `/access`, `/activity` and `/invitations` accept optional responsibilityScopeId as a project filter. Without it, they include all projects of the current companies. Administrator role gates remain in force. A project-filtered candidate appears if they have an application in that project; a candidate without applications uses their original project as a fallback. Detail includes related applications, tasks, contacts and events across that company. Internal `/candidate` and `/import-row` may omit scope: the server resolves it from the record ID and checks company authorization. Internal `/visits` accepts `{}`; `/request-views` may resolve the project from requestId.

All writes retain explicit original responsibilityScopeId. New applications, application contacts and linked tasks use the request/application scope. An unlinked contact uses the candidate's scope. External grants and invitations continue to assign requests within one explicit project; list rows include responsibilityScopeId for editing the original assignment. Internal assignees may have personal-data access in any project of the company; external assignees still require the exact project and request assignment.

Migration 054 changes candidate-reference foreign keys to `(candidate_id, legal_entity_id)`. Application-to-request and linked task/contact-to-application tuples stay exact. Existing project metadata, IDs, phone duplicates and history are preserved; nothing is moved, merged or backfilled. Company locks precede sorted project locks so candidate changes cannot race cross-project reference validation. Omitting scope never opens a company collection for an external recruiter.

### Request

`title` required max160; `city` max100, required for open requests; `district` max160; `kind` driver|carrier; `quantity` integer1..10000 for open requests, null or integer0..10000 for paused/closed; `priority` normal|urgent; `status` open|paused|closed; `neededBy` nullable date; `recruiterId` eligible UUID required; `schedule` max300; `payTerms` max1000; `vehicleRequirements` max1000; `notes` max4000; `hhUrl` max2048; `publishedAt` nullable ISO instant (manual publication record); `requiresSecurity` boolean default false. Omitting requiresSecurity when updating preserves its current value. Only manager/dispatcher/access_admin may change an existing request's security requirement. Server createdAt is demand start; publishedAt must not precede creation. Publication lag explicitly based on manual timestamps, not API verification.

### Candidate

`fullName` required max160; `phone` required normalized Russian/international E164 (8 -> +7, 10 digits -> +7), new records and phone changes are checked for duplicates across the company; unchanged historical duplicates remain editable; `city` required max100; `district` max160; `kind` driver|carrier; `recruiterId` required eligible UUID; `source` manual|avito|ati|hh|referral|vehicle_sticker|telegram|whatsapp|rabota_ru|superjob|joblab|profi|other; `hhUrl` max2048; `licenseCategories` max80; `experience` max500; `vehicleType` max160; `vehicleDimensions` max160; `vehicleCapacity` max160; `notes` max4000; `archived` boolean default false. The unique phone is a duplicate warning boundary, not automatic evidence that two people are identical. This release has no separate shared-contact entity for several people using one phone.

### Application

`candidateId`, `requestId` required same-company UUIDs; responsibilityScopeId is the request project; candidate/request kind must match; unique candidate+request pair; `recruiterId` required eligible UUID; `stage` new|contact|qualified|interview|security|internship|paperwork|hired|reserve|rejected; `reason` max1000 (required when rejected); `startDate` nullable date, required when hired (planned start, not factual confirmation). Candidate/request links immutable. On create/stage change append immutable event `{id,applicationId,fromStage:null|string,toStage,occurredAt,actorId}`. Request closed prevents new applications, permits existing updates. If requiresSecurity is true, a transition into internship/paperwork/hired requires existing securityStatus approved. Do not auto-decrement request quantity based on unverified 1C facts.

Read-only workflow fields: `securityStatus`, `securityAssigneeId`, `securityDueAt`, `attendanceStatus`, `confirmedStartDate`, `confirmedBy`, `confirmedAt`. Generic application PUT never writes these fields. Existing manual hires migrate with attendanceStatus unconfirmed. Use the dedicated commands below for decisions and factual confirmation.

### Task

`candidateId` nullable same-company UUID; `applicationId` nullable same-scope UUID; `title` required max300; `dueAt` required ISO instant; `assigneeId` required eligible UUID; `status` open|done; `notes` max2000. An application fixes the candidate reference and must be available to both the actor and an external assignee. An existing task's application access is checked before changing or removing that reference. Store completedAt on transition done; clear if reopened. Read-only `workflowKind` is manual|security. Security tasks cannot be changed through generic PUT or completed through a contact; only the security command manages them. Reminders are in-app while open, durable across server/browser restarts.

## Daily workflow API (migration 036)

These endpoints use the same current-session, personal-data company and external request checks as ordinary recruitment writes. Company and project advisory locks serialize reference checks and mutations. Security/start updates use application versions; contact creation uses a caller-provided UUID as its idempotency key.

- GET `/worklist?responsibilityScopeId=...&view=all&page=1&pageSize=25` returns `{items,total,page,pageSize,counts,cities,requests,recruiters,requestRecruiters,workflowOperators,permissions,integrations,serverTime,timeZone}`. Each item is `{candidate,applications,tasks,lastContact}`. Optional filters: `search` max200, `city` max100, `kind`, `stage`, `source`, `recruiterId`, `archived=true|false`. Page size is 1..100; candidates sort by updatedAt descending, then id. `archived=false` is the default; true selects archived records. Counts use the current filters and count candidates. Views: all, new, today, overdue, security, starts, no_next. Today uses each candidate project region's timezone; personal task queues use the selected assignee. External users cannot request another recruiter's records.
- GET `/candidate?responsibilityScopeId=...&candidateId=...&contactPage=1&contactPageSize=50` returns the candidate, applications, tasks, stage events, contacts, workflow events and the same relevant directory/permission fields. Contacts paginate separately (1..100 per page) with contactTotal. Stage and workflow event histories each expose up to 500 newest events and eventsTruncated/workflowEventsTruncated. This is explicit truncation, not complete history export.
- POST `/contacts` body: `{id,responsibilityScopeId,candidateId,applicationId?,result,source?,occurredAt?,notes?,completeTaskId?,nextAction?}`. Result: inquiry|connected|no_answer|callback|thinking|declined. An inquiry requires source; other contacts default to the candidate's source without changing that source. occurredAt is an ISO instant at or before server time, defaulting to server time. notes max4000. nextAction is `{title,dueAt,assigneeId}`, with title max300 and dueAt in the future; mandatory for no_answer/callback/thinking. Optional completeTaskId must be an open manual task for this candidate/application and executable by the current actor (or manager/access_admin). Writes the contact, next task and optional completion atomically; returns `{contact,task}`. Identical retries return the existing result, changed payload returns 409. A replay cannot return an unrelated task sharing a UUID. Declined does not automatically reject applications.
- POST `/security` body: `{responsibilityScopeId,applicationId,version,status,assigneeId?,dueAt?,note?}`. Status: not_requested|documents|submitted|in_review|clarification|approved|rejected|not_required. Note max2000. Operators are manager/dispatcher/access_admin. Nonoperators may prepare documents or submit them, cannot assign a different checker or change an approved/rejected decision. Checkers must be active, approved operators with personal-data access in the same company. Dispatcher cannot override another assigned checker; manager/admin override requires a note. Rejected/clarification require a note. Submitted/in_review/clarification require an assigned checker and a future deadline. Documents preserves the previous deadline when omitted and does not complete an existing checker task. An assigned open task prevents a reset to not_requested; approved/rejected/not_required close the checker task. An obligatory security requirement prevents not_required. Maintains the dedicated checker task and appends an immutable workflow event. Returns the saved application.
- POST `/start-confirmation` body: `{responsibilityScopeId,applicationId,version,status:'confirmed'|'no_show',date?,note?}`. Operators only; application must be at hired. Confirmed requires a real date not later than the region's current date and a positive security decision when required. No-show or amendment of an already confirmed result requires a note. Stores attendanceStatus and, for a confirmation, date/actor/time; appends a workflow event. Returns the saved application. This is a staff confirmation, not a 1C shift.

Contact responses contain id, candidateId, applicationId, result, source, occurredAt, recordedAt, actorId, notes and origin (app|import). Imported inquiry dates may be null. Contact source and candidate source are separate facts. External responses exclude imported contacts and other actors' contacts; application-linked contacts/tasks must belong to currently assigned requests even if the candidate remains accessible through another request. Workflow decision notes are omitted for nonoperators, and other actors' IDs in workflow/stage events are masked for external users. Request notes/sourceDetails remain excluded from external directories.

Successful contact creation also appends server-authored activity kind contact_recorded in the same transaction. Activity report rows expose contactsRecorded (distinct recorded contact/inquiry IDs in the reporting window), which counts as substantive work for the attention signal. Exact retries, failed saves, import and impersonation do not increment it. This measures saved records, not verified phone conversations; client-supplied actor metadata cannot change attribution.

The first release pages candidates and contacts; legacy full-scope tabs still use the bounded snapshot. Generic PUT limits remain 10,000 records of each primary type and 50,000 stage events per scope. Worklist directories/related rows also fail explicitly above their 10,000-row bounds. New endpoints do not provide channel expenses, retention, shift counts, automatic messaging or a real-time source spreadsheet sync.

## Named internal recruiter onboarding

`GET /api/v1/access/employees/options` includes recruiterCreationEnabled and recruiterScopes, limited to the administrator's current personal-data scopes. `POST /api/v1/access/employees/recruiter` accepts `{displayName,scopeId,idempotencyKey}`; access_admin only, no impersonation. Creates one active/approved recruiter with sourceKind internal_manual, financeVisible false and personalDataVisible true in that authorized scope. It is independent of demo settings. Exact concurrent retries return the same employee; changed payload conflicts. Account creation is audited and does not issue a password automatically. Continue with the established `/access/users/:id/password` flow.

`POST /api/v1/access/employees/recruiter-scope` accepts `{userId,scopeId}`. The target must already be an active/approved recruiter fully manageable by the administrator. It adds the authorized scope with financeVisible false/personalDataVisible true, is naturally idempotent and audited, and does not change role, name or credentials. Existing incompatible flags conflict rather than silently elevating or replacing grants. The UI uses «Добавить рекрутера» and «Добавить область работы» on an existing employee card. No account migration is needed beyond the existing internal_manual source kind introduced in migration 032.

## Frontend

New module `recruitment.js` exports `createRecruitmentPanel(React,{request})` and `createRecruitmentReminder(React,{request})`.
Panel props `{token,actor,onExpired,onDirtyChange,taskRequest,reminderScopeId}`. Reminder props `{token,onExpired,onOpen}`; global small notice/button invokes `onOpen(firstDueTask.responsibilityScopeId)`. Root increments taskRequest; internal users open their tasks across the company after context loads; external users retain the assigned project selection. Poll at 60s; refresh on focus and `recruitment:changed`, abort unmounted. No sensitive previews outside allowed scope. Root integrates in existing navigation for roles above, dirty confirmations, module hashing, CSS.

UI Russian, real empty states, request and candidate create/edit, application-stage updates, due tasks/complete, company-wide default with an optional project filter and city/kind/recruiter/search filters, visible pipeline cards, candidates list incl unlinked, request list, reminder list, analytics. Current-stage counts labelled «Сейчас по этапам»; conversion from events distinct applications ever entering stages clearly separated from current counts. Filters consistently affect summary. Show manual hire count, no fabricated shifts/retention; integrations status honest. External hh links use HTTPS allowed hosts, target _blank rel noopener noreferrer. Candidate card has hh button, tel link, history, linked applications and tasks. Exact date/time reminders use browser local time with explicit timezone label. Responsive theme-compatible styling. Unsaved forms guarded across scope/tab/section changes and beforeunload. Use accessible labels and clear conflict/error messages.

## External recruitment extension (migrations 028–029)

Request fields add `warehouseAddress` (max500), `routeInfo` (max1000), `trainingTerms` (max1000), `driverRequirements` (max1000), `publicBrief` (max4000), all optional strings. Existing `notes` is internal. Externally readable fields must be explicitly selected; company notes and request-owner identity are excluded. The source register has two directions: Проекты (`driver`, people) and Перевозчики (`carrier`, vehicles).

`POST /api/v1/access/employees/external` with `{displayName,scopeId,idempotencyKey}` is administrator-only, requires that administrator's personal-data grant in the selected scope, creates role `external_recruiter` with no finance access, and returns the employee summary directly. It is a real account, sourceKind `external_manual`, independent of demo creation settings. Exact retries return the same account; changed payload conflicts. No demand assignment or password is created implicitly. Use existing `POST /api/v1/access/users/:id/password` separately and show returned credentials only to the administrator.

`POST /api/v1/access/employees/external-scope` with `{userId,scopeId}` attaches an active external account already fully manageable by the administrator to another permitted personal-data scope. Concurrent retries are idempotent; no password or demand assignment changes.

- GET `/access?responsibilityScopeId=...` (under recruitment) returns `{users,grants}` for a manager/access_admin in scope.
- PUT `/access`: `{responsibilityScopeId,userId,requestIds,status:'active'|'revoked',expiresAt,version}`. Assignments are a complete versioned list of same-scope request IDs. New requests never inherit a previous all-current selection. Revocation and expiry affect the next server operation.
- GET `/activity?responsibilityScopeId=...&days=7|30|90`: company-only report `{days,periodStart,periodEnd,rows,metricDefinitions,attentionThresholds,retentionDays}`. Rows describe the actor who performed each action, while the funnel retains ownership by assigned recruiter. Hires are manual stage events, not verified shifts.
- POST `/visits`: `{responsibilityScopeId}` records explicit section/scope entry. POST `/request-views`: `{responsibilityScopeId,requestId}` records explicit detail opening. Server supplies actor/session/time. Repeats deduplicate by session, scope, type, request where applicable, and 30-minute bucket. Impersonation is excluded from performance metrics.
- Successful data snapshots also record `data_read` on the server; separate `dataReads` counts expose access performed without the UI event calls. Background access checks use context, not full snapshots.

External read/write restrictions apply inside current-session transactions: assigned requests only; owned candidates/applications/tasks; candidate and request references must remain allowed; cannot create/update requests or assign someone else. Candidates attached exclusively to withdrawn requests are hidden. Context excludes inaccessible scopes; reminders recheck assignment and ownership. The external API surface outside recruitment is closed in AuthGuard except own identity and stopping administrator impersonation. Communications bot identity and queued Telegram/MAX delivery additionally reject this role.

Activity events permit SELECT/INSERT to transport_app, without UPDATE/DELETE. Candidate creation, application creation/stage changes, task completion and contact creation are recorded from successful writes in the same transaction. Report begins with recorded events after deployment, with no invented historic browsing. Signal rule: at least 7 days of observation, at least 5 active days or 20 explicit request views in the window, zero new candidates/applications, saved contacts/inquiries, forward progress, manual hires or completed tasks. The UI explains the rule as a manual review cue, never an accusation or automatic access block. No automatic event deletion is configured; report windows are not retention limits.

## Self-service invitations (migration 030)

Administrator-only routes `/api/v1/recruitment/invitations` require an active `access_admin` session, no impersonation, and that administrator's current personal-data grant in the target company; the invitation itself still selects one exact project:

- POST with `{responsibilityScopeId,requestIds,expiresAt?,accessExpiresAt}` creates an invitation for explicit current requests. Link expiry defaults to 7 days, is capped at 30 days and cannot exceed access expiry. The response includes the random `invitationToken` once; only its SHA-256 hash is stored.
- GET `?responsibilityScopeId=...` returns `{invitations,truncated}`, at most 1,000 newest records, without raw tokens or hashes.
- POST `/:id/revoke` with `{responsibilityScopeId}` revokes an unused link. An accepted invitation's access is managed through the existing recruitment access endpoints.

Public routes use `/api/v1/recruitment-invitations`:

- POST `/preview` with `{token}` returns `{ready:true,expiresAt}` for a valid invitation. No names, phone numbers, scope or project information is disclosed.
- POST `/accept` with `{token,displayName,phone,password,mode:'new'}` creates a real external account with `sourceKind:external_invitation`. Name and normalized phone are self-entered; phone ownership is not SMS-verified. Password length is 12–128 characters. Existing-account mode uses `{token,phone,password,mode:'existing'}` and requires that external account's actual credentials, without altering its name or password. Existing staff accounts cannot become external accounts through this route.

Acceptance revalidates current issuer privileges, scope, requests, expiry, revocation and consumption under database locks, and atomically creates/attaches the account, assigns demand, consumes the invitation, writes audit and issues a session. Exactly one concurrent acceptance succeeds. Active prior request assignments are retained only when the existing and invited scope expiries match exactly. Different expiries return 409 `RECRUITMENT_INVITATION_ACCESS_CONFLICT`, leaving both access and the pending invitation unchanged, so an administrator can reconcile the scope's single access period. Other scopes are unchanged. A fresh invitation can explicitly reopen previously revoked/expired scope access. Pending invitations and accepted access are separate revocations: revoke both when withdrawing both authorizations.

New and existing modes share password attempt throttling; public endpoints also have IP limits. Acceptance requires the trusted authentication origin and `X-Session-Refresh: 1`. Successful acceptance expires the previous remembered-login cookie and returns a tab session with `rememberedDevice:false`. Errors do not replace the prior identity. There is no automatic notification or message delivery.

Frontend exports `createRecruitmentInvitationPanel(React,{request})`, props `{invitationToken,onAuthenticated,onCancel}`. The invitation is encoded in the URL fragment `#recruitment-invite=TOKEN`, sent only in POST JSON, never persisted in browser storage, and removed after acceptance/cancel. This page takes priority over an existing session and postpones session restoration and third-party messenger SDK loading. Acceptance shares the normal device-auth lock; stale session restores cannot replace the new identity. The standalone form works at mobile widths. Administrator creates/copies the link with no name/phone entry; loopback links are explicitly labelled as local-only.

## Source workbook import (migration 031)

Request validation now requires positive quantity 1–10000 and nonblank city only for `status:open`. Paused/closed requests allow explicit `quantity:null`, integer 0–10000, and empty city. Other entities retain their existing validation. Null is rendered «Не уточнено», zero remains zero, and the edit form does not convert an empty quantity to zero.

Requests have `source_details` text, max100000 characters, returned as `sourceDetails` only to staff. It is excluded from the external request allowlist. The generic create/update parser ignores supplied `sourceDetails`, and ordinary saves preserve the stored value. The runtime DB role has no write privilege on this new column. A guarded administrative local importer populates the source and record together. The UI displays it as literal text in a collapsed staff-only reference block, without HTML interpretation or a source edit field.

## Reviewed candidate workbook import (migration 038)

`integrations/recruitment-candidates-import/prepare.py` reads the two principal candidate sheets without recalculation or writes to the workbook. It creates private batch/archive/resolution/summary JSON files with source hashes, original cell values/formulas and issues. Archive sheets are not converted to live records. `import-local.cjs` offers preview (default, read-only), dry-run (full transaction rolled back) and apply (atomic commit). This is a local administrator CLI, not a public upload API or synchronization service.

Explicit decisions map each selected row to an existing authorized scope, direction, internal recruiter, source and optional existing demand. Identity resolution is new/existing/another selected new record; duplicate phones require a reviewed choice. Existing candidates and applications are never overwritten. Each row creates an inquiry contact with origin import and optional unknown occurredAt; a new application may start only at new or reserve, while reuse preserves its current state. The importer creates no users, grants, demands, stage events, security approvals, start confirmations or follow-up tasks from historical spreadsheet flags.

`recruitment_candidate_imports` stores document/source/row/resolution hashes, scope and resulting candidate/contact/application IDs plus private source and resolution JSON. It has no transport_app grants and is not exposed through recruitment APIs. Identical replay skips imported rows even after subsequent app edits; changed source or decisions for an imported row conflict. Audit includes identifiers/hashes rather than original personal data. See [RECRUITMENT_MIGRATION.md](RECRUITMENT_MIGRATION.md) for the operational preparation and review sequence.
