# Настройка доступа к планированию

Администратор доступа настраивает диспетчеров и менеджеров в разделе **«Сотрудники»**. Для планирования сотруднику нужна назначенная область работы с разрешением на персональные данные: планы и клиентские заявки могут содержать телефоны и документы водителей.

## Существующий диспетчер или менеджер

1. Найдите сотрудника в разделе «Сотрудники» и нажмите **«Настроить планирование»**.
2. Выберите одну или несколько доступных областей работы.
3. В областях, где сотрудник должен планировать рейсы, включите **«Разрешить доступ к персональным данным»**.
4. Сохраните настройки. Сотрудник обновляет раздел «Планирование» и выбирает проект из доступных вариантов.

Область работы определяется сочетанием юридического лица, региона, проекта и зоны ответственности. Например: «Компания → Москва → Городская доставка → Дневная группа». Сотрудники с доступом к одной зоне работают с общим планом на выбранную дату. Список содержит уже заведённые области, доступные администратору.

Отключение персональных данных закрывает планирование в соответствующей области. Удаление области снимает все связанные с ней права сотрудника; интерфейс требует подтвердить это действие. Нужно оставить хотя бы одну область работы; для полного отключения учётной записи используется существующая кнопка «Отозвать доступ».

## Новый сотрудник

Кнопка **«Добавить диспетчера / менеджера»** создаёт обычную именную учётную запись. Укажите имя, роль и область работы, проверьте разрешение на персональные данные. После создания откроется штатная выдача пароля по телефону. Создание доступно независимо от режима тестовых профилей.

## Ограничения и сохранение

Администратор может назначить только собственные области и передать разрешение на персональные данные только при наличии такого разрешения у него самого. Чужие, заблокированные и не полностью управляемые аккаунты недоступны для изменения. Вход от имени другого сотрудника не позволяет управлять правами.

Изменение областей выполняется целиком: при ошибке ни одна область не меняется. Если другой администратор уже изменил права, сохранение отклоняется с предложением загрузить актуальные настройки. Пароль и роль существующего сотрудника сохраняются. Финансовые и специальные разрешения в оставленных областях не меняются, новым областям финансовый доступ не выдаётся. Изменения записываются в журнал аудита. Сервер учитывает новые права в следующих запросах текущей сессии.

## Проверки

Из каталога `recovered`:

- `npm run test:planning:access` — создание, настройка, ограничения администратора, отзыв прав, конфликты и целостность сохранения на временной базе.
- `npm run test:planning:access:browser` — путь администратора и диспетчера в браузере с синтетическими данными.
- `npm run build` — сборка API и интерфейса.

Для проверки готовой сборки задайте `PLANNING_BUILT_FRONTEND=true`; при необходимости укажите `PLAYWRIGHT_MODULE` и `CHROME_PATH`.

## API и установка

- `GET /access/employees/options` возвращает доступные роли и области для создания диспетчера/менеджера.
- `POST /access/employees/planner` создаёт именной аккаунт с защитой от повторного запроса.
- `GET /access/employees/:employeeId/planning-access` возвращает назначенные области, пределы полномочий администратора и версию настроек.
- `PUT /access/employees/:employeeId/planning-access` сохраняет полный набор областей и разрешения на персональные данные с проверкой версии.

Миграция `065_planning_access_management.sql` и базовые разрешения в `scripts/migrate.cjs` позволяют серверу изменять флаг персональных данных и снимать область. Прямое изменение финансового разрешения серверной роли не предоставляется. Миграция не изменяет назначения сотрудников.
