# Operational fleet replacement contract

User explicitly requested full daily workflow: vehicles, work orders, repairs, scheduled maintenance, parts, contractors, stock, purchasing, fuel and drivers, plus downloadable PPTX reports. Existing operations/trips/inspection modules remain intact. Implement a native fleet workspace, not only workbook views. No invented stock/fuel/assignment balances from historical orders.

## Ownership

Root writes fleet-operations-input.js (validation/domain), fleet-operations.js frontend + CSS, report generator, wiring and tests. Backend agent (reconciliation) writes fleet-operations.module.js + 035_fleet_operations.sql after finishing analytics backend, integration tests. Core agent keeps parser/model and then supports tests/review.

## Persisted entities

Scoped record table `fleet_ops_records`: id UUID, kind enum below, full four scope IDs, version integer, payload jsonb, created_by/updated_by, timestamps. Keys id globally unique, foreign references validated exact scope and kind. Additional immutable events and stock movements. Every accepted mutation versioned and audited; no hard deletes. Counters per scope may allocate visible order numbers, but UUID is stable. Data input id UUID (new records supplied by browser), version 0 for create.

All endpoints prefix `/fleet-operations`. Entity payload fields below, strings default empty, nullable numbers/dates. Validation function `parseRecord(kind,body)` returns `{id,responsibilityScopeId,version,payload}`; rejects unknown kind and invalid fields. Domain exports `KINDS,parseRecord,orderRows,maintenanceStatus` and `validateAction`.

- vehicles: `{plate,vin,brand,model,year,group,status:'active'|'repair'|'retired',odometerKm,fuelType,notes}`. Uniqueness normalized plate among active records and VIN when nonblank. Import existing source vehicles with an explicit action, preserve source plate history via analytics links.
- contractors: `{name,phone,email,notes,active}`.
- parts: `{sku,name,unit,minStock,active}`.
- warehouses: `{name,notes,active}`.
- orders: `{number,vehicleId,openedOn,completedOn,status:'draft'|'in_progress'|'completed'|'cancelled',odometerKm,contractorId|null,execution:'unknown'|'internal'|'contractor',responsible,complaint,notes,driverReportId|null,maintenanceId|null,lines:[{id,type:'работа'|'запчасть',name,group,node,quantity,unit,unitPriceCents,discountPercent,adjustmentCents,adjustmentReason,amountCents,partId|null,warehouseId|null,stockSource:'none'|'warehouse'}]}`. Server computes amountCents, ignores submitted total; positive quantity at most3decimals; price integer cents, discount0..100; negative adjustment requires reason; no implicit returns. Draft/new may only draft/in_progress; completion only action. Completed/cancelled records cannot generic edit. Completing deducts all warehouse parts atomically, stock sufficiency verified, exactly-once by state+idempotency key. A warehouse-linked line must reference a part/warehouse. Total source count/amount equals mapped rows. Source original imports immutable, new orders have prefixed orderId `app:<uuid>` to avoid duplicate counting with imported numeric IDs. Cancel only uncompleted orders; reopen completed not supported without explicit reversal workflow and never silently restock.
- maintenance: `{vehicleId,title,intervalKm|null,intervalDays|null,lastCompletedOn|null,lastOdometerKm|null,dueOn|null,dueOdometerKm|null,active,notes}`. At least date or km threshold/interval. Due derived from explicit due or last+interval. Completing an associated repair records lastCompletedOn/lastOdometerKm, clears explicit threshold, computes next. Overdue/due soon uses date current UTC and vehicle latest odometer; no invented odometer.
- purchases: `{number,contractorId,warehouseId,orderedOn,status:'draft'|'ordered'|'received'|'cancelled',notes,lines:[{id,partId,quantity,unitCostCents}]}`. Status received only action; receiving adds stock once atomically. All lines part refs; no receival into inactive warehouse. Received immutable. Purchasing does not add repair expense until consumption.
- fuel: `{vehicleId,date,fuelType,litres,unitPriceCents,amountCents,odometerKm|null,fullTank,station,receiptReference,notes,driverUserId|null}`. Server computes amountCents from litres×unit price; litres>0 up to3decimals. Managers can record, driver submits via report. No fabricated consumption L/100km; report litres/cost and calculate only valid full-tank intervals if implemented.
- assignments: `{vehicleId,driverUserId,startsOn,endsOn|null,notes,active}`. Driver must active role driver in exact granted scope, no arbitrary cross-scope user. Dates valid; same vehicle/driver active overlapping assignments rejected. Allows mobile driver workflow.
- driverReports: `{vehicleId,driverUserId,reportedOn,type:'defect'|'fuel'|'odometer',description,odometerKm|null,litres|null,unitPriceCents|null,fullTank,station,receiptReference,status:'new'|'accepted'|'resolved'|'rejected',orderId|null,resolution}`. Created by drivers only for assigned vehicles/date; root staff may create on behalf. Read-only other people's reports to driver forbidden. Acceptance fuel posts fuel once; odometer updates known latest reading with no backwards roll; defect acceptance leaves open for order linkage. Resolve requires resolution; close linked order resolves report. All transitions guarded and idempotent.

Stock table immutable per movement `{id,scope,partId,warehouseId,quantityMilli bigint signed,unitCostCents,amountCents signed,kind:'opening'|'receipt'|'issue',documentId,createdAt,createdBy}`. Balance quantity sum, valuation amount sum. Receipt positive. Issue negative uses weighted average current available value / qty, caps rounding correctly final issue drains remaining value. Orders expense amount independent supplier source; warehouse lines on completion use actual issued valuation as amount (never duplicate receipt as repair expense), update line amounts auditably. Initial balances via POST `/stock/opening` body `{idempotencyKey,scope,partId,warehouseId,quantity,unitCostCents,reason}` reason required, no negative opening. Stock adjustments/reversals can be later explicit workflow, no direct balance editing.

## Access and HTTP

Staff reads role access_admin/manager/mechanic/auditor with financeVisible grant, writes except auditor. Session revalidation and exact tuple on every endpoint, same pattern as analytics. Driver endpoint separately allows actor.role driver with exact assignment and current scope grant, costs of others never returned.

- GET `/context` -> same analytics scopes for staff, driver scopes only assigned access.
- GET `?responsibilityScopeId=...` -> `{records:{vehicles:[],contractors:[],parts:[],warehouses:[],orders:[],maintenance:[],purchases:[],fuel:[],assignments:[],driverReports:[]},stock:[{partId,warehouseId,quantity,amountCents}],drivers:[{id,displayName}],maintenance:[{id,vehicleId,label,status,dueOn,dueOdometerKm,remainingKm,remainingDays}],events:[...]}`. Record `{id,kind,version,...payload,createdAt,updatedAt}`. Cap explicitly fail, never truncate actual sums.
- PUT `/:kind` body parsed record -> flattened record. Scope comes body, kind allowed constant only. No client-controlled sums/posting status.
- POST `/:kind/:id/action` `{responsibilityScopeId,version,action:'start'|'complete'|'cancel'|'order'|'receive'|'accept'|'resolve'|'reject',idempotencyKey,completedOn?,resolution?}` -> `{record}`. Actions according to kind. Retry idempotency key same response, different payload409. Driver cannot call staff routes.
- POST `/stock/opening` as above -> `{stock}`.
- POST `/vehicles/import` `{responsibilityScopeId,idempotencyKey}` -> `{created,existing,needsReview}` creates cards from current source dataset, no overwrite existing, no guessed VIN or stable alias. Use latest valid reading by date (historical anomalies remain analytics warnings). Only explicit action triggered after data import by UI/root authorized installation.
- GET `/driver` -> `{assignments:[record+vehicle],reports:[own records]}` derived only own actor, scopes checked. No costs or staff data beyond own report payload. POST `/driver/reports` validated minimal `{id,version:0,responsibilityScopeId,vehicleId,reportedOn,type,description,odometerKm?,litres?,unitPriceCents?,fullTank?,station?,receiptReference?}` forces driverUserId=actor and status=new. Driver read report statuses.

## Analytics integration

Analytics service must merge current imported rows with `orderRows(opsRecords)` from all noncancelled native orders; filters default all matches old semantics, completed native maps Финиш, drafts Старт, active В процессе. Stock purchases/fuel NOT included in repair KPI. Additional ops totals shown as fuel separately in workspace/PPTX, no double count. Analytics CSV and PPTX use same combined full filtered source. If no XLSX dataset but native orders exist, still return valid analytics. Context UI shows native count plus imported filename, never says no data for native-only records.
