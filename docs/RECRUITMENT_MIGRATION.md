## Порядок переноса

1. Сохранить исходник и подготовить отдельный реестр разбора: лист, строка, диапазон объединения, исходное значение, предлагаемое поле, замечание. Формулы и значения фиксировать отдельно. Объединения раскрывать только в пределах фактического диапазона, без протягивания через другие проекты.
2. Сначала перенести согласованные условия проектов. Разделить строки с разными складами, ролями, графиками и оплатой на отдельные однородные заявки. Проверить адреса, единицы потребности и принадлежность к существующей области доступа.
3. Сверить активную потребность с заказчиком: количество, срок, ответственный, оплата, график, требования, дата подтверждения. Нулевые, скрытые и противоречивые строки оставить в реестре разбора. Не создавать из них открытые заявки автоматически.
4. Подготовить `publicBrief` и остальные условия, разрешённые сторонним рекрутерам. Контакты заказчиков, внутренние обсуждения и сведения о других кандидатах сохранить во внутренних полях. Перед предоставлением доступа проверить фактическое содержимое всей выдаваемой карточки.
5. Создать только подтверждённые заявки. Пока проверка не закончена, держать запись в реестре разбора либо сохранять согласованную заявку со статусом `paused`, без внешнего доступа. Не подставлять вымышленные количество, срок или ответственного ради обязательных полей.
6. Пригласить сторонних рекрутеров по одноразовым ссылкам, выбрав конкретные заявки и срок доступа. Каждый рекрутер вводит свои имя, телефон и пароль сам. Для уже заведённых аккаунтов можно назначить потребности напрямую. Проверить внешний просмотр, отсутствие чужих кандидатов и внутренних заметок, затем сделать приложение источником актуальной потребности. Старую таблицу сохранить как архив и прекратить двойное редактирование.

Для повторного переноса нужен реестр соответствий «исходный файл / лист / строка → ID заявки» и проверка версии существующей записи. Повтор не должен создавать дубли или заменять более свежие изменения приложения.

### Решения до записи в базу

Сначала создать именные штатные аккаунты через «Сотрудники → Добавить рекрутера» или использовать существующих сотрудников. Затем указать их UUID в `recruiters`, существующую разрешённую область и направление driver/carrier в `targets`, значения справочника в `sources` и UUID прежних потребностей в `demands`. Название листа само по себе не подтверждает направление, проект или личность ответственного. Импорт не создаёт пользователей, разрешения, проекты или потребности.

Для каждой выбранной строки `resolution.records["лист:строка"]` требуется явное решение:

- `action`: pending (оставить на разборе), exclude (с непустой reason) либо import.
- `disposition`: active или archive. Пустая причина отказа в Excel не определяет активность кандидата.
- `acknowledgedIssues`: все отмеченные проблемы этой строки после их проверки.
- `candidate`: `{mode:"new"}`, `{mode:"existing",id:"UUID"}` или `{mode:"record",sourceKey:"лист:строка"}` для явно подтверждённого повторного обращения к новой карточке из этого пакета.
- `demand`: none, UUID существующей потребности или mapped для значения из общего справочника. При создании участия допустим только проверенный начальный stage new или reserve. Уже существующее участие требует `application:"reuse"` и сохраняет текущий этап.
- Необходимые исправления имени, телефона, города или даты задаются в `corrections` вместе с непустым пояснением `evidence`.

Совпадение нормализованного телефона не объединяет записи автоматически. Два разных решения new на один номер в одной области вызывают конфликт. Привязка к existing требует совпадения области, направления, владельца и телефона; существующая карточка не перезаписывается. Один контакт перевозчика, представляющий разных людей, нужно разобрать вручную: отдельной модели общих телефонов в первом релизе нет.

Исходные галочки собеседования, СБ, стажировки, трудоустройства и увольнения остаются источником для проверки. Они не создают события прохождения этапов, положительное решение СБ, подтверждённый выход или новые задачи. Каждая выбранная строка создаёт отдельное обращение с `origin=import`. Непроверенные, будущие, ошибочные и вычисляемые даты остаются `occurredAt=null`; время импорта хранится отдельно. Отсутствие исторической даты не заменяется текущей датой.

### Предварительная проверка, пробный перенос и применение

CLI по умолчанию работает в режиме preview и подключается только к настроенному постоянному локальному приложению; удалённый URL или `.env` он не принимает. Сопоставленные записи проверяются от имени активного локального администратора с действующими правами на персональные данные. Для применения нужны миграции 036 и 038.

```sh
node integrations/recruitment-candidates-import/import-local.cjs --preview --directory .local/recruitment-candidate-import
node integrations/recruitment-candidates-import/import-local.cjs --dry-run --directory .local/recruitment-candidate-import
node integrations/recruitment-candidates-import/import-local.cjs --apply --directory .local/recruitment-candidate-import
```

Preview использует транзакцию только для чтения и показывает проблемы выбранных строк; при полностью незаполненной карте база не открывается. Dry-run выполняет ту же запись и аудит, что apply, затем откатывает транзакцию. Apply фиксирует выбранные проверенные строки атомарно; конфликт отменяет пакет целиком. Отчёты `preview.json`, `dry-run.json` и `apply.json` сохраняются в закрытом каталоге. Перед реальным apply следует иметь актуальную резервную копию постоянной локальной базы; CLI не создаёт её автоматически.

ID карточки, обращения и происхождения детерминированы по документу и строке. Повтор идентичного пакета не создаёт дубли и не отменяет последующие правки рекрутеров в приложении. Изменённые исходные значения, снимок или решения для уже перенесённой строки возвращают конфликт, а не обновляют карточку автоматически. Повторная история импортированной строки не становится новой активностью рекрутера.

Миграция `038_recruitment_candidate_import.sql` хранит закрытый реестр происхождения: SHA-256 источника, ключ строки, принятые решения и исходные данные. Обычная роль приложения `transport_app` не имеет доступа к этому реестру. Внешнему рекрутеру импортированные контакты и исходные служебные данные не выдаются. Журнал аудита содержит идентификаторы и контрольные суммы без исходных персональных комментариев. Отдельного браузерного просмотра этого административного реестра нет.

Для перехода команды сначала выбрать один проект и сотрудников, сверить незавершённые обращения и ближайшие действия, применить проверенный пакет, затем зафиксировать момент переключения. Автоматическая загрузка изменений Google Sheets и повторное сопоставление произвольно изменённого файла не реализованы. Новые изменения таблицы между подготовкой и переключением требуют отдельной сверки. До этого подготовленный пакет не следует считать актуальным рабочим реестром.

Проверки на синтетических данных: `integrations/recruitment-candidates-import/test-prepare.py` и `tests/recruitment-candidate-import.test.cjs`. Проверяются неизвестные даты, архив, явные решения по дублям, неизменность существующих записей, отсутствие вымышленных событий, разрешения и повторный запуск.

## Общая база компании — миграция 054

`054_company_recruitment.sql` разрешает использовать существующего кандидата в потребности другого проекта того же юрлица. Ссылки из подборов, задач и контактов на кандидата проверяют пару `candidate_id, legal_entity_id`; ссылки на потребность и подбор сохраняют полный проектный ключ. Изменение не переносит, не удаляет и не объединяет строки. Исторические одинаковые телефоны в разных проектах сохраняются.

Доступ на уровне компании вычисляется только внутри рекрутинга из текущих `personalDataVisible` grants. Сохранённые `access_grants` не расширяются; остальные модули и ограничения внешних рекрутеров не меняются. Применять 054 вместе с обновлённым API: прежний код не поддерживает ссылки кандидатов между проектами. Проверка на одноразовой БД: `node --test tests/recruitment-company-integration.test.cjs` из корня проекта.
