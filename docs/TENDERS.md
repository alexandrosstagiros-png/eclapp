# Тендеры и доступ специалиста

## Добавление сотрудника администратором

1. Открыть **Сотрудники → Добавить тендерного специалиста**.
2. Указать имя сотрудника и выбрать область работы.
3. Нажать **Создать сотрудника**.
4. В открывшейся форме указать телефон и выдать пароль для входа.

Это обычная учётная запись с ролью «Тендерный специалист», а не демо-профиль.
Её создание доступно и при выключенном создании тестовых сотрудников.
Сам сотрудник при входе попадает в «Тендеры». Администратор также видит этот
раздел в меню и может проверить доступ кнопкой «Войти как сотрудник».
Специалист работает только в назначенной области; доступ к финансам,
кадровым персональным данным, рекрутингу и управлению сотрудниками не выдаётся.
Существующее маскирование имени сотрудника для администраторов без разрешения
на персональные данные сохраняется. Такого сотрудника можно найти по номеру и роли.

## Ежедневная работа

Кнопка **+ Новый тендер** создаёт карточку по заказчику. Для начала достаточно
названия заказчика и названия тендера/проекта. У одного заказчика может быть
несколько карточек. Повторно выбирать существующего заказчика предпочтительнее
создания одноимённой компании.

Доска содержит этапы **Запланировано → В работе → Ждём решения → Выиграно**.
Статус меняется списком на самой карточке. Для победы сохраняется подтверждённый
результат, для закрытия — причина. Закрытые карточки доступны отдельной кнопкой.

На карточке доступны количество авто (включая диапазон), требования, тип доставки,
ожидаемый запуск, следующий шаг и его срок. Дедлайн подачи заявки хранится отдельно
от даты начала работы. Неопределённый запуск можно сохранить текстом без выдуманной даты.

Комментарий добавляется прямо на доске. На ней показан последний именно комментарий:
смена этапа его не заменяет. **Карточка и история →** открывает подробности и хронологию.
Переключатель **Весь заказчик** показывает события связанных тендеров этого заказчика.
Закрытие и повторное открытие не удаляют предыдущие комментарии и причины результата.

Изменения сохраняются на сервере. При конфликте версий интерфейс показывает свежие
данные и оставляет черновик для явной сверки. Повтор отправки комментария после
сетевой ошибки использует прежний идентификатор и не создаёт дубль.

## Канбан и таблица

Переключатель **Канбан / Таблица** меняет отображение тех же карточек.
В таблице кнопка **Колонки** открывает выбор видимых полей. **По умолчанию**
возвращает исходный набор. Столбец «Заказчик / тендер» остаётся видимым,
чтобы можно было открыть карточку и историю.

Статус меняется прямо в строке; **Написать комментарий** открывает поле ввода.
Черновик комментария сохраняется при переключении между видами. Закрытые
карточки доступны в обоих видах. Вид, набор колонок и выбранная область
сохраняются отдельно для каждого пользователя в текущем браузере.

Ссылка на область имеет вид `?section=tenders&responsibilityScopeId=<UUID>`.
Она открывается только при наличии доступа; чужие области не становятся доступны.

## Состав обновления

- Миграция `032_tenders.sql`: роль, обычный источник сотрудника `internal_manual`,
  заказчики, тендеры и неизменяемая история событий.
- API `/tenders`: контекст, данные области, сохранение заказчика/тендера и комментарии.
- Создание сотрудника: `POST /access/employees/tender-specialist`.
- Интерфейс `tenders.js`, стили `tenders.css`, меню и форма в `app.js`.
- Поддержка сборки и постоянного локального приложения ЕЦЛ.

## Перенос Excel

Локальный скрипт `integrations/tenders-import/import-local.cjs` переносит проверенный
план из `.local/tenders-import/plan.json`. По умолчанию выполняется пробная транзакция
с откатом; `--apply` сохраняет результат. Миграция `033_tender_import_events.sql`
выделяет исходные заметки в события `import`, отличающиеся от новых комментариев.

План для «КЛИЕНТУРА общий 11.09.xlsx» покрывает 29 строк листа «Лист2»:
28 заказчиков и 28 карточек, полностью одинаковые строки 5 и 17 объединены.
Дословные A:E, адреса всех исходных ячеек и SHA256 файла сохраняются в истории.
Сроки без года остаются текстом; этапы и типы работы предварительно определены
по смыслу исходных записей, без автоматического присвоения победы.

Исходные B/C показаны как **Исходная заметка · дата неизвестна** до первого
обычного комментария. Время переноса не считается датой исходного действия.
Повтор неизменённого импорта ничего не добавляет; изменения источника или
ранее перенесённых карточек приводят к отказу без перезаписи. Весь перенос
выполняется одной транзакцией. Права специалисту выдаются администратором
на область **Тендеры · Клиентура → Клиентская база** обычным способом.

Правила переноса описаны в [концепции](TENDERS_CONCEPT.md).
Отчёт за период из концепции пока не реализован; доступна история событий.

## Проверки

`npm test`, `npm run test:integration` — модульные и интеграционные проверки.
`npm run test:tenders` — отдельная проверка модуля и ограничений доступа.
`npm run test:tenders:browser` — браузерный сценарий на одноразовой PostgreSQL.
`node --test tests/tenders-workbook-import.test.cjs` из корня — проверка
пробного переноса, атомарности, повторов, сохранности источника и прав.
Для него можно задать `PLAYWRIGHT_MODULE`, `CHROME_PATH` и `TENDERS_BUILT_FRONTEND=true`.

Рабочие учётные записи, клиенты и тендеры тестами не создаются. Проверки используют
синтетические данные в отдельных временных базах.
