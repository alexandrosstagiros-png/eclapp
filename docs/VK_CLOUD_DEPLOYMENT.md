# Установка и обновление ЕЦЛ в VK Cloud

Схема установки: Ubuntu 24.04 с Node.js 22 и Nginx, отдельная PostgreSQL 17
в приватной сети, один публичный HTTPS-адрес приложения. Kubernetes не требуется.
Код установки находится в `deploy/vk-cloud/`, workflow —
в `.github/workflows/deploy-vk-cloud.yml`.

Наличие этих файлов в репозитории не означает, что сервер уже настроен.
Автоматические обновления включаются только после первого проверенного запуска.

## Подготовка сети и доступов

- Подключите ВМ и БД к одной приватной сети. Запишите приватные IP обоих сервисов.
- Разрешите TCP 5432 на БД только от приватного IP/группы сервера приложения.
  Базе не нужен внешний IP.
- Откройте 80/443 для приложения. SSH 22 разрешите администраторам и выбранному
  источнику деплоя. Обычные GitHub-hosted runners не имеют одного постоянного
  исходящего IP; ограничение SSH только домашним IP не позволит им подключиться.
  Используйте runner с контролируемым адресом либо ручной деплой с доверенного
  компьютера. Не устанавливайте runner для публичного репозитория на рабочую ВМ.
- При двух интерфейсах ВМ проверьте внутри Ubuntu приватный адрес и маршруты
  (`ip -brief address`, `ip route`). Подключение порта в панели не подтверждает,
  что гостевая ОС получила адрес. Доступ к БД и внешний SSH должны работать
  одновременно; не меняйте основной маршрут без резервной консоли.
- Выберите HTTPS-адрес приложения: публичный IP или домен. Для домена направьте
  DNS A-запись на внешний IP ВМ. Значения `app.example.com` и `203.0.113.10`
  ниже являются примерами; замените их своим адресом.

Первый SSH-вход выполняется административным ключом, скачанным при создании ВМ.
На компьютере ограничьте права файла: `chmod 600 /полный/путь/ключ.pem`.
Имя пользователя Ubuntu проверьте в инструкции подключения к конкретной ВМ.
Сверьте fingerprint SSH с ключом в консоли сервера; не подтверждайте неизвестный
ключ автоматически. Пароли БД и приватные ключи не должны попадать в Git.

## Установка серверного окружения

Загрузите на ВМ проверенную копию **всего репозитория**, включая `deploy/`,
`integrations/` и `recovered/`, и выполните из её корня:

```sh
sudo bash deploy/vk-cloud/bootstrap.sh
```

Сценарий устанавливает Node.js 22, PostgreSQL client 17, Nginx и Certbot,
пользователей `ecl-deploy`, `ecl-build`, `ecl-migrate`, `ecl-app` и службу
`ecl-app.service`. Сборка, миграции и приложение запускаются разными системными
пользователями. Код приложения не запускается от root.

Установленные привилегированные помощники:

- `/usr/local/sbin/ecl-deploy` — принимает архив и точный commit SHA;
- `/usr/local/sbin/ecl-configure-nginx` — готовит конфигурацию HTTPS;
- `/usr/local/lib/ecl/` — вспомогательные файлы.

Изменения `bootstrap.sh`, `deploy.py`, настроек systemd или привилегированных
помощников требуют отдельной проверки администратором и повторной установки
из проверенной версии. Обычный выпуск приложения не должен автоматически
заменять привилегированный механизм своего деплоя.

## Подключение PostgreSQL и выбор данных

Используются два набора реквизитов:

| Файл на ВМ | Назначение |
| --- | --- |
| `/etc/ecl/app.env` | `DATABASE_URL` ограниченного пользователя `transport_app` и настройки приложения |
| `/etc/ecl/migration.env` | `MIGRATION_DATABASE_URL` владельца схемы и `APP_DB_PASSWORD` пользователя `transport_app` |

Создавайте файлы из `deploy/vk-cloud/app.env.example` и
`deploy/vk-cloud/migration.env.example`, сохраняйте с владельцем
`root:root` и правами `0600`. Оба файла задают `NODE_ENV=production`.
Их читает systemd и передаёт окружение нужному
процессу. Не копируйте локальный `.env` целиком: локальные домены, тестовые флаги,
пути к 1С и временные секреты для облака не подходят.

В URL соединения используйте приватный адрес БД и реально созданное имя базы.
Специальные символы логина/пароля кодируются для URL; `APP_DB_PASSWORD` содержит
исходный пароль, без URL-кодирования. Его значение должно совпадать с паролем
в `DATABASE_URL` и иметь длину не менее 20 символов. Реквизиты администратора БД
не добавляются в окружение работающего API или в GitHub Actions.

Примеры окружения требуют TLS с проверкой сертификата (`sslmode=verify-full`).
В VK Cloud шифрование может быть выключено у созданного инстанса. Чтобы
включить его, откройте карточку БД, вкладку **«Параметры баз данных»**, добавьте
`ssl` со значением `on` и сохраните изменение с подтверждением. Инстанс
перезагрузится; выполните это до начала работы сотрудников. PgBouncer для
включения TLS не обязателен.
[Инструкция VK Cloud по TLS](https://github.com/vk-cs/docs-public/blob/master/docs/ru/dbs/dbaas/how-to-guides/tls-connect/tls-connect.md).

Инструкция провайдера предлагает проверять зашифрованное подключение через
`sslmode=require`, но не описывает получение CA и имя сервера для полной
проверки сертификата. Для примеров этого репозитория дополнительно нужны
доверенный CA и адрес, соответствующий сертификату: уточните их у VK Cloud,
если стандартная проверка не проходит. Не считайте сертификат доверенным лишь
потому, что его прислал сервер при первом сетевом подключении.

Ответ `N` на PostgreSQL SSLRequest означает, что этот endpoint сейчас не
принимает TLS. Клиентский параметр URL не включает TLS на сервере. Не обходите
ошибку проверки сертификата через `rejectUnauthorized=false` или
`NODE_TLS_REJECT_UNAUTHORIZED=0`. Приватная сеть сама по себе не заменяет
шифрование. Режим `sslmode=disable`, также описанный в
[инструкции подключения VK Cloud](https://github.com/vk-cs/docs-public/blob/master/docs/ru/dbs/dbaas/connect/connect.md),
передаёт данные без TLS и не является автоматическим запасным режимом этих
примеров.

Миграции создают/изменяют роль `transport_app`, таблицы, функции, триггеры,
выдают права и используют `pgcrypto`. Поэтому `transport_admin`, созданный
через мастер VK Cloud, должен иметь необходимые полномочия владельца схемы
и управления этой ролью. Одного имени с суффиксом `_admin` недостаточно.
В управляемой PostgreSQL заранее проверьте доступность `pgcrypto`, право
`CREATE ROLE`/`ALTER ROLE` и владение импортированными объектами. Если сервис
ограничивает эти действия, настройте разрешения через администратора сервиса
до первого выпуска; не запускайте API с повышенными правами в качестве обхода.

До первого рабочего запуска явно выберите источник данных:

1. Для переноса существующих пользователей и рабочих данных восстановите
   согласованную резервную копию в **новую пустую** облачную базу. Зафиксируйте
   момент прекращения записи в старую базу, чтобы не потерять изменения после
   выгрузки. Не смешивайте базы с локального компьютера и старого сервера.
2. Сохраните `schema_migrations` и проверьте владельцев объектов после
   восстановления. Деплой применит только недостающие миграции и остановится
   при несовпадении контрольной суммы уже применённой миграции.
3. Для новой пустой базы миграции создадут схему, но **не создадут рабочую
   организацию и администратора**. После первого выпуска используйте
   `recovered/scripts/bootstrap-production.cjs` с настоящими данными, как
   описано ниже. `scripts/seed.cjs` предназначен только для development/test.
4. `recovered/scripts/bootstrap-password.cjs` задаёт первый пароль уже
   существующему единственному активному `access_admin` с областью доступа.
   Он не создаёт администратора. Вывод с одноразовым паролем храните приватно,
   не в логе CI. При переносе существующих пользователей их парольные записи
   сохраняются вместе с базой.

Не выполняйте восстановление поверх базы, которой уже пользуются сотрудники,
без отдельного согласованного плана и актуальной резервной копии.

Для полностью новой базы подготовьте `/etc/ecl/bootstrap.json` с владельцем
`root:root`, правами `0600` и полями `phone`, `name`, `password`,
`organizationName`. Используйте реальный телефон администратора и уникальный
пароль; файл нельзя сохранять в репозитории. После первого выпуска и миграций
остановите API перед созданием администратора. До успешного завершения bootstrap
оставьте Nginx в режиме `--acme-only`: публичные попытки входа могут добавить
записи в базу и помешать проверке её пустоты.

```sh
sudo systemctl stop ecl-app
sudo systemd-run --unit=ecl-production-bootstrap --wait --pipe --collect \
  --property=User=ecl-migrate --property=Group=ecl-migrate \
  --property=WorkingDirectory=/opt/ecl/current/recovered \
  --property=EnvironmentFile=/etc/ecl/migration.env \
  --property=LoadCredential=bootstrap.json:/etc/ecl/bootstrap.json \
  --property=NoNewPrivileges=yes --property=ProtectSystem=strict \
  /usr/bin/node scripts/bootstrap-production.cjs \
  --config /run/credentials/ecl-production-bootstrap.service/bootstrap.json
```

Сценарий требует пустую полностью мигрированную базу и создаёт организацию,
область доступа и одного администратора атомарно. Он не печатает пароль и не
перезаписывает существующие данные. Только после успешного завершения снова
запустите API, затем включите HTTPS по инструкции ниже:

```sh
sudo systemctl start ecl-app
```

После проверки входа удалите временный файл `bootstrap.json`; пароль храните
в менеджере паролей. При ошибке bootstrap оставьте API остановленным и проверьте
причину, прежде чем открывать приложение пользователям.

## HTTPS и первый запуск

Если домена пока нет, можно выпустить сертификат непосредственно на публичный
IP. Для IP-сертификатов через `webroot` нужен Certbot 5.4 или новее и профиль
`shortlived`; bootstrap устанавливает отдельную совместимую версию.
[Инструкция Let's Encrypt](https://letsencrypt.org/2026/03/11/shorter-certs-certbot).

```sh
sudo /usr/local/sbin/ecl-configure-nginx 203.0.113.10 --acme-only
sudo /opt/ecl-certbot/bin/certbot certonly --webroot \
  --webroot-path /var/www/letsencrypt --ip-address 203.0.113.10 \
  --preferred-profile shortlived --cert-name ecl-app
```

После первого ручного выпуска и успешного создания администратора включите HTTPS:

```sh
sudo /usr/local/sbin/ecl-configure-nginx 203.0.113.10 \
  --certificate /etc/letsencrypt/live/ecl-app/fullchain.pem \
  --certificate-key /etc/letsencrypt/live/ecl-app/privkey.pem
```

В `ALLOWED_ORIGINS` укажите тот же адрес `https://ВАШ_ПУБЛИЧНЫЙ_IP`.
Для IP-сертификата особенно важна работа автоматического продления: его срок
действия — шесть дней. Не закрывайте HTTP-доступ к ACME-проверке после выдачи.

Для своего домена после настройки DNS сначала откройте только выдачу
ACME-проверки:

```sh
sudo /usr/local/sbin/ecl-configure-nginx app.example.com --acme-only
sudo /opt/ecl-certbot/bin/certbot certonly --webroot -w /var/www/letsencrypt -d app.example.com
```

Установите первую версию вручную по процедуре ниже: она создаст статические
файлы, запустит API и подготовит CSP. Для новой базы затем остановите API,
создайте администратора и снова запустите API по инструкции выше. После этого
включите HTTPS:

```sh
sudo /usr/local/sbin/ecl-configure-nginx app.example.com \
  --certificate /etc/letsencrypt/live/app.example.com/fullchain.pem \
  --certificate-key /etc/letsencrypt/live/app.example.com/privkey.pem
```

Bootstrap устанавливает отдельный Certbot и таймер `ecl-certbot-renew.timer`,
который проверяет продление дважды в день и перезагружает Nginx после
обновления сертификата. Проверьте `systemctl list-timers ecl-certbot-renew.timer`
и `sudo /opt/ecl-certbot/bin/certbot renew --dry-run`. API слушает только
`127.0.0.1:3001`, Nginx публикует HTTPS. Настройки внешнего адреса приложения
должны содержать тот же HTTPS-домен.

После первого выпуска и настройки HTTPS проверьте:

```sh
sudo systemctl status ecl-app --no-pager
curl --fail http://127.0.0.1:3001/api/v1/health/ready
curl --fail https://app.example.com/api/v1/health/ready
```

Затем проверьте вход реального администратора, его права, основные разделы,
чтение/запись данных и загрузку документов. Успешный readiness подтверждает
доступность процесса и базы, но не заменяет проверку пользовательских сценариев.
Журнал сервиса доступен через `sudo journalctl -u ecl-app`; не публикуйте
содержимое журнала без проверки на рабочие данные.

## Обновления из GitHub

Создайте отдельную SSH-пару для деплоя. Добавьте публичную часть в
`/home/ecl-deploy/.ssh/authorized_keys` с владельцем `ecl-deploy`, правами `0600`
и префиксом `restrict`, отключающим forwarding, PTY и пользовательский rc-файл.
Этот ключ предназначен только для выпуска приложения; скачанный ключ
администратора ВМ в GitHub не требуется.

В **Settings → Secrets and variables → Actions → Secrets** репозитория добавьте:

| Secret | Значение |
| --- | --- |
| `VK_DEPLOY_HOST` | Публичный IPv4 или DNS-имя ВМ, без `https://` и порта |
| `VK_DEPLOY_SSH_KEY` | Приватный ключ отдельной пары деплоя |
| `VK_DEPLOY_KNOWN_HOSTS` | Проверенная строка `known_hosts` для этого же адреса |
| `VK_DEPLOY_USER` | Необязательно: по умолчанию `ecl-deploy`; стандартная установка использует именно его |

Ключ хоста возьмите из `/etc/ssh/ssh_host_ed25519_key.pub` через доверенную
консоль/уже проверенное подключение сервера. Строка для секрета имеет вид
`АДРЕС_ВМ ssh-ed25519 ПУБЛИЧНЫЙ_КЛЮЧ_ХОСТА` — это публичный ключ **сервера**,
а не публичная часть пары пользователя деплоя. Если хост переустановлен,
повторно проверьте fingerprint и обновите секрет. Workflow не доверяет
результату нового `ssh-keyscan` при каждом запуске.

После проверки сервера и первого выпуска добавьте в **Variables** репозитория
`VK_DEPLOY_ENABLED` со значением `true`. Пока переменная не установлена, workflow
пишет, что деплой выключен, и не обращается к серверу.

Порядок обновления:

1. Pull request проходит существующий workflow `CI`.
2. После объединения в `main` выполняется CI для push в `main`.
3. `Deploy VK Cloud` проверяет, что завершённый CI относится к текущему
   commit SHA `main` в исходном репозитории, и только затем загружает код.
4. На ВМ собирается выпуск, создаётся резервная копия БД и применяются миграции;
   переключение на выпуск завершается проверкой readiness.

Workflow не запускает деплой из pull request или fork. Для одного сервера
выпуски сериализованы; работающая установка не прерывается новым push.
GitHub может заменить ожидающий запуск более новым, поэтому каждый запуск
проверяет текущий `main` ещё раз перед вызовом установки.

Ручной **Actions → Deploy VK Cloud → Run workflow → main** также берёт текущий
`main` и требует успешный последний push CI **для того же SHA**. Это повторный
выпуск текущего `main`, а не способ обойти проверки или выбрать старую ветку.
Исправляйте приложение через PR; rollback кода предпочтительно оформлять
новым revert-коммитом, совместимым с текущей схемой базы.

Повторный запуск для уже работающего здорового SHA завершится без переустановки.
Если каталог этого SHA остался после неудачного выпуска, сценарий остановится:
администратор должен сначала проверить причину сбоя и состояние миграций,
затем убрать только неактивный неудачный выпуск перед повторной попыткой.
Не удаляйте каталог текущей или предыдущей рабочей версии.

## Ручная доставка при недоступном SSH из GitHub

С доверенного компьютера используйте тот же архив и серверный сценарий.
Предварительно проверьте успешный push CI для выбранного текущего `main`:

```sh
git fetch origin main
deploy_sha=$(git rev-parse origin/main)
git archive --format=tar.gz --output="/tmp/$deploy_sha.tar.gz" "$deploy_sha"
```

Настройте в локальном `~/.ssh/config` alias `ecl-production` с адресом ВМ,
пользователем `ecl-deploy`, отдельным ключом, `IdentitiesOnly yes`,
`StrictHostKeyChecking yes` и заранее проверенным `known_hosts`. Затем:

```sh
scp "/tmp/$deploy_sha.tar.gz" "ecl-production:/home/ecl-deploy/incoming/$deploy_sha.tar.gz"
ssh ecl-production "sudo /usr/local/sbin/ecl-deploy /home/ecl-deploy/incoming/$deploy_sha.tar.gz $deploy_sha"
```

Архив содержит только отслеживаемые Git файлы на указанном SHA. Незакоммиченные
изменения, `.env`, ключи, `node_modules` и локальная база в него не добавляются.
Серверный сценарий проверяет путь и формат SHA, но сам не запрашивает GitHub:
при ручной доставке проверка происхождения версии и результата CI лежит на
администраторе. Не передавайте произвольный сторонний архив под доверенным SHA.

## Резервные копии, восстановление и эксплуатация

Перед миграциями сценарий делает PostgreSQL custom dump и сохраняет последние
14 таких копий в `/var/backups/ecl/db` с доступом только root. Неудачная выгрузка
останавливает выпуск. Эти копии находятся на ВМ и не заменяют автоматические
резервные копии управляемой БД, PITR и отдельное защищённое хранилище.

Фотографии оформления хранятся вне выпусков в
`/var/lib/ecl/onboarding-photos`. Они **не входят в `pg_dump`**. Определите для
них отдельную политику хранения/резервирования с учётом автоматического
удаления оригиналов через 72 часа и ограничений доступа к документам.
Копии не должны незаметно продлевать срок хранения персональных документов.
Остальные файлы, хранимые в таблицах БД, входят в дамп базы.

Если новая версия не проходит readiness, сценарий возвращает предыдущий код,
когда он существует. Уже успешно применённые миграции при этом сохраняются.
Возврат кода безопасен только для совместимых изменений схемы; восстановление
БД из копии — отдельная операция с простоем и возможной потерей новых записей.
Первый выпуск не имеет предыдущей версии для возврата.

Настройте внешний мониторинг HTTPS/readiness, оповещения о сбоях резервного
копирования и заполнении дисков ВМ/БД, контроль памяти, CPU, соединений БД
и срока сертификата. Пробное восстановление в отдельную базу подтверждает
пригодность копий лучше, чем само наличие файлов.

Локальный обмен планами с 1С в текущем коде привязан к локальному окружению и
не заработает только от переноса приложения в облако. Ему потребуется отдельный
проект подключения через согласованный защищённый канал. Интеграции MAX,
уведомлений и OCR также включаются только после настройки их рабочих адресов
и серверных секретов. Отсутствие этих интеграций не означает, что перенос
основного приложения завершён с проверкой всех прежних функций.
